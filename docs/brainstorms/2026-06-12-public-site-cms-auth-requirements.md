## Проблема

У компании «Комплект» нет единого портала: публичный сайт существует отдельно, а ERP — отдельно. Контент сайта правится разработчиком. Заявки с сайта не попадают автоматически в систему.

## Цель

Один портал: публичный маркетинговый сайт + CMS для самостоятельного редактирования контента + вход для сотрудников — всё в рамках одного Next.js приложения.

---

## Акторы

| ID | Актор | Описание |
|----|-------|----------|
| A1 | Посетитель | Анонимный пользователь сайта, потенциальный клиент |
| A2 | Директор / контент-редактор | Сотрудник ERP с доступом к CMS-разделу дашборда |
| A3 | Сотрудник ERP | Любой пользователь с аккаунтом; входит через `/login` |
| A4 | Администратор | Создаёт аккаунты сотрудников через `/dashboard/admin/users` |

## Этап 1 — Публичный сайт

### Страницы

| Путь | Содержание |
|------|-----------|
| `/` | Главная: hero-блок, преимущества, этапы работы, отзывы, форма заявки |
| `/about` | О компании: история, лицензии, реквизиты, виды деятельности |
| `/services` | Виды деятельности: Электроснабжение, Газоснабжение, Водоснабжение, Водоотведение, Строительство |
| `/services/[slug]` | Детальная страница услуги |
| `/contacts` | Контакты: телефоны, email, карта, реквизиты |
| `/privacy` | Политика конфиденциальности |
| `/terms` | Пользовательское соглашение |

### Ключевые потоки (F)

**F1 — Просмотр сайта (A1)**
Посетитель открывает любую публичную страницу — контент отдаётся без аутентификации.

**F2 — Отправка формы заявки (A1)**

1. Посетитель заполняет форму (Имя, Телефон, Email?, Тип услуги, Комментарий).
2. Фоновая проверка reCAPTCHA v3 / Cloudflare Turnstile.
3. POST на публичный endpoint → создаётся `Request` со `source=WEBSITE`, `status=NEW`.
4. Посетитель видит сообщение «Заявка принята, мы свяжемся с вами».
5. Менеджер видит заявку в `/dashboard/requests`.

**F3 — Вход сотрудника (A3)**
Кнопка «Войти» в хедере сайта → переход на существующий `/login` → после успеха → `/dashboard`. Новых auth-роутов нет.

### Acceptance Examples (AE)

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| AE-1 | Посетитель открывает `/` без авторизации | Страница отдаётся, 200 OK, нет редиректа на /login |
| AE-2 | Посетитель отправляет форму с валидными данными | HTTP 201, в ERP создан Request, посетитель видит подтверждение |
| AE-3 | Форма отправлена без имени/телефона | Валидация на фронте блокирует отправку |
| AE-4 | Бот отправляет форму с низким score reCAPTCHA | HTTP 422, заявка не создаётся |
| AE-5 | Сотрудник нажимает «Войти» | Переход на /login, после входа → /dashboard |
| AE-6 | Сотрудник открывает `/` | Публичный сайт (НЕ редирект на /dashboard) |

## Этап 2 — CMS внутри ERP

### Раздел `/dashboard/cms/`

Доступен пользователям с ролью, имеющей право `cms.write`.

| Подраздел | Редактируемый контент |
|-----------|-----------------------|
| Главная | Заголовок hero, подзаголовок, текст CTA, преимущества (список), этапы (список) |
| О компании | История (rich-text), миссия, лицензии (список с файлами), реквизиты |
| Виды деятельности | Для каждой услуги: название, описание (rich-text), иконка/изображение |
| Контакты | Телефоны, email, адрес, координаты карты |
| SEO | title, description, og:image для каждой страницы |
| Баннеры | Изображения + ссылки для hero-секции |
| Фотогалерея | Загрузка изображений (S3/локально), подписи |

### Ключевые потоки (F)

**F4 — Редактирование контента (A2)**

1. Директор открывает `/dashboard/cms/about`.
2. Редактирует текст в rich-text редакторе (TipTap или аналог).
3. Нажимает «Сохранить» → PATCH `/api/v1/cms/pages/{slug}/`.
4. Контент немедленно отображается на публичной странице.

### Acceptance Examples (AE)

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| AE-7 | Директор меняет текст на главной и сохраняет | Публичная страница `/` отдаёт новый текст без деплоя |
| AE-8 | Пользователь без `cms.write` открывает `/dashboard/cms/` | 403 |
| AE-9 | Директор загружает изображение для баннера | Файл сохраняется, URL появляется в CMS |

## Этап 3 — Вход

Сотрудники входят через существующий `/login`. Публичный сайт содержит кнопку «Войти» в хедере/навигации.

- Самостоятельная регистрация сотрудников — **вне скопа**.
- Аккаунты создаются только через `/dashboard/admin/users` (A4).
- Изменений в auth-логике нет.

## Границы скопа

### Не в скопе (этих задач здесь нет)

- Кабинет клиента / личный кабинет для внешних пользователей
- Самостоятельная регистрация сотрудников через сайт
- Страница «Сотрудники» (команда)
- Блог / новостной раздел
- Мобильное приложение

### Деferred (возможный следующий этап)

- Онлайн-оплата заявок
- Трекинг статуса заявки для клиента без кабинета (по ссылке / SMS-коду)
- Многоязычность

## Зависимости и допущения

| # | Тип | Описание |
|---|-----|----------|
| D1 | Зависимость | Текущий ERP-роутинг: `/` → редирект на `/dashboard`. Нужно убрать редирект, `/` становится публичной Главной |
| D2 | Зависимость | Публичный endpoint формы заявки — вне RBAC-middleware. Требует отдельного Django-роута без `@require_permission` |
| D3 | Зависимость | Защита публичного endpoint: **Cloudflare Turnstile** (сайт за CF proxy) + rate limiting на уровне CF/Django |
| D4 | Допущение | **Один tenant, config-based**. `tenant_id` фиксирован в переменной окружения `PUBLIC_SITE_TENANT_ID`. Публичный endpoint использует его напрямую — без domain lookup. При необходимости SaaS в будущем заменяется на domain→tenant таблицу без изменения клиентского кода. |
| D5 | Допущение | CMS-контент хранится per-tenant в БД (Django-модели), не в файлах |
| D6 | Допущение | Next.js публичные страницы — SSR или ISR с on-demand revalidation при сохранении CMS |
| D7 | Допущение | Загрузка файлов/изображений в CMS идёт через существующий files-модуль (S3) |
