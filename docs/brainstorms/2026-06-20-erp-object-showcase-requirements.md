# Sprint #5 — Public Object Showcase: Наши объекты

## Summary

Раздел «Наши объекты / Наши работы» на публичном сайте компании: фильтруемый каталог объектов снабжения с карточками и страницами деталей. Операторы вручную помечают объекты как публичные и загружают обложку. Раздел напрямую поддерживает воронку заявок — посетитель видит реализованные проекты, убеждается в компетенции компании и оставляет заявку.

Фото объекта и чистый URL важнее GIS-данных и SEO-разметки на этом этапе.

---

## Пользовательские сценарии

**Посетитель публичного сайта:**
- Открывает `/objects/` и видит каталог объектов с фильтрацией по типу ресурса (электричество, газ, вода, тепло)
- Каждая карточка: обложка, название, адрес, бейдж типа ресурса
- Переходит на `/objects/transformatornaya-podstanciya-ivanova` и видит детальную страницу: фото, описание, адрес, мини-карту (если есть геометка)

**Оператор (внутренний):**
- Открывает карточку объекта в дашборде → переключатель «Опубликовать на сайте» — независимо от статуса объекта
- Загружает обложку для объекта
- Видит и может отредактировать slug (автоматически генерируется из названия при создании)

## Требования

### Изменения модели SupplyObject

| Поле | Тип | Значение по умолчанию | Nullable | Назначение |
|------|-----|----------------------|----------|------------|
| `is_public` | BooleanField | `False` | НЕТ | Ручной флаг публикации на сайте, независим от `status` |
| `slug` | SlugField, unique per tenant | авто из `name` | НЕТ | SEO-дружественный URL-идентификатор |
| `cover_image_key` | CharField (S3 key) | пусто | ДА | Ключ обложки в S3; если не задан — карточка без фото |

**`is_public` — только BooleanField(default=False), NOT NULL. Tri-state не нужен: объект либо публичен, либо нет.**

### Публичный API (apps/objects)

Новый маршрут в `apps/objects` — без аутентификации, без RBAC:

```
GET /api/v1/objects/public/
GET /api/v1/objects/public/{slug}/
```

**Фильтры каталога:** `?resource_type=ELECTRICITY|GAS|WATER|HEAT`

**Скоп тенанта:** `PUBLIC_SITE_TENANT_ID` из Django settings (настройка уже определена в `config/settings/base.py`). Все публичные запросы к объектам фильтруются по этому tenant_id.

**`PublicObjectSchema` — публично отдаём только:**

| Поле | Примечание |
|------|-----------|
| `id` | UUID |
| `slug` | |
| `name` | |
| `address` | |
| `resource_type` | enum: ELECTRICITY, GAS, WATER, HEAT, OTHER |
| `object_type` | enum: BUILDING, GRS, PIPELINE, SUBSTATION, RESERVOIR, HEATING_POINT, OTHER |
| `status` | опционально — директор решает показывать ли |
| `description` | |
| `cover_image_url` | presigned S3 URL или `null` |
| `location` | GeoJSON Point или `null` |

**Никогда не отдаём:** `manager_id`, `foreman_id`, `contragent_id`, `contract_id`, внутренние комментарии, финансовые данные, `tenant_id`.

### Публичный сайт (Next.js)

Новые маршруты в группе `(public)`:

| Маршрут | Страница |
|---------|---------|
| `/objects/` | Каталог с фильтром по типу ресурса (табы или чипы) |
| `/objects/[slug]/` | Деталь объекта |

**Карточка в каталоге:**
- Обложка (placeholder если нет)
- Название
- Адрес
- Бейдж типа ресурса

**Страница детали:**
- Обложка
- Название, описание
- Адрес, тип ресурса
- Мини-карта — **только если `location` задан**; если нет — карта не отображается (не обязательна)

### Cover Image

- `cover_image_key` задан → отображаем фото из S3
- `cover_image_key` не задан → placeholder-иконка или пустое место (без broken image)
- Upload механизм (через `apps/files` ClamAV pipeline или прямой S3) — решение при планировании

### Карта

- Компонент Leaflet (тот же, что в дашборде)
- Показывается только при наличии PointField `location`
- Мини-формат (нет панели управления, нет слоёв)
- Центрируется на координате объекта

## Архитектурные решения

### Domain Isolation (ADR-0005)

Фронтенд вызывает `apps/objects` публичный endpoint напрямую — нет Python-кросс-импорта между `apps/site` и `apps/objects`. ADR-0005 сохраняется.

```
Visitor browser
     │
     ├──► GET /api/v1/site/cms/{slug}/         → apps.site
     └──► GET /api/v1/objects/public/          → apps.objects
```

`apps/site` не знает ничего об `apps/objects`. Никакого Outbox, никаких snapshot-таблиц.

### Snapshot vs. Direct Query

Выбираем **прямой запрос**. ~100 объектов, 1 компания, низкая нагрузка. Snapshot-денормализация добавит сложность без пользы.

### Миграция (ADR-0002: Expand & Contract)

`is_public` и `slug` — новые столбцы, добавляются как nullable в Release N, backfill в Release N+1 (если нужен), NOT NULL в Release N+2. `cover_image_key` остаётся nullable.

## Вне скопа (Sprint #5)

| Что | Почему отложено |
|-----|----------------|
| SEO: OpenGraph, Schema.org, sitemap | Следующий этап — сначала вывести объекты |
| GIS: ЗОУИТ, кадастровая привязка | Отдельный спринт (есть отдельный брайншторм) |
| Outbox / snapshot-денормализация | Не нужна при текущей нагрузке |
| Gallery (несколько фото) | Только обложка сейчас |
| Форма заявки на странице объекта | Глобальная форма на публичном сайте покрывает это |

## Открытые вопросы (для планирования)

1. **Cover image upload:** интегрировать с существующим `apps/files` (ClamAV pipeline) или добавить прямой S3 upload отдельным полем? Первый подход безопаснее, второй — проще для Sprint #5.
2. **Slug generation:** автогенерация при сохранении (`pre_save` signal) или explicit action? Нужна ли защита от коллизий (суффикс `-2`, `-3`)?
3. **Placeholder для обложки:** дизайн-решение — иконка типа ресурса, градиентный фон, или просто пустое место?
4. **Показывать ли `status` на публичной странице?** Директор решает — зафиксировать как настраиваемое или hardcode.
