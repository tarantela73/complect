# Карта: поиск по адресам, кадастровым номерам и слой ЗОУИТ

## Контекст

В `/dashboard/map` уже есть карта (Leaflet + react-leaflet) с маркерами объектов, слоями
Кадастр (PKK6 тайлы) и Коммуникации (OpenRailwayMap), провайдерами OSM/Яндекс/2ГИС.
Нужно добавить поиск и улучшить слой коммуникаций.

## Проблема

Пользователь не может найти конкретный участок или адрес на карте — приходится вручную
скролить/зумить. Также слой "Коммуникации" (OpenRailwayMap) показывает только железные
дороги, а не охранные зоны инженерных сетей, которые критичны при планировании работ.

## Акторы

- **A1** — Инженер/менеджер проекта: ищет участок по кадастровому номеру или адресу,
  проверяет наличие охранных зон рядом с объектом.

## Ключевые сценарии

**F1 — Поиск по адресу:**
Пользователь вводит адрес в поисковую строку → автокомплит выдаёт варианты (dебаунс 300ms)
→ выбирает результат → карта летит к точке (`flyTo`, zoom 16).

**F2 — Поиск по кадастровому номеру:**
Пользователь вводит кадастровый номер (формат `NN:NN:NNNNNNN:N`) → запрос к PKK API
→ карта летит к геометрии участка → граница участка подсвечивается пульсирующим полигоном
поверх всех слоёв → клик по другому месту — полигон снимается.

**F3 — Слой охранных зон (ЗОУИТ):**
Пользователь включает "Коммуникации" → поверх базового слоя накладываются охранные зоны
газопроводов, ЛЭП, водоканалов, линий связи из Росреестра PKK6/ZONES.
Заменяет текущий OpenRailwayMap — он релевантен только для ж/д, не для инженерных сетей.

## Решения

### Геокодер адресов: DaData Suggestions API
- Эндпоинт: `POST /suggestions/api/4_1/rs/suggest/address`
- Возвращает ФИАС-структуру + `geo_lat`, `geo_lon`
- Free tier 10 000 запросов/день — достаточно для внутреннего ERP
- API-ключ: `NEXT_PUBLIC_DADATA_API_KEY` (клиентский env var — приемлемо для internal app)
- Дебаунс 300ms, минимум 3 символа для запроса

### Поиск по кадастрам: PKK REST API
- Эндпоинт: `GET https://pkk.rosreestr.ru/api/features/1?text={cad_num}&limit=1`
- Возвращает GeoJSON геометрию участка + центроид
- Публичный API, без ключа, тот же домен что и тайлы кадастра (уже в CSP)
- Подсветка: Leaflet `Polygon` с `dashArray`, z-index выше маркеров

### Слой коммуникаций: Росреестр PKK6 ЗОУИТ
- Тайловый сервис PKK6 (аналогичный формат ArcGIS REST, как уже работающий CadastreObjects)
- Отображает охранные зоны: ЛЭП, газопроводы, нефтепроводы, водоканал, линии связи
- Заменяет OpenRailwayMap в `OPENINFRA_TILES` константе
- Слой начинает рендериться от zoom ≈ 10 (так же как и кадастр)

### UX: единая строка поиска
Один `<input>` в тулбаре карты с placeholder "Адрес или кадастровый номер...".
Логика определения типа запроса:
- Regex `/^\d{2}:\d{2}:\d{7}:\d+$/` → кадастровый поиск (PKK API)
- Иначе → адресный поиск (DaData)

Никаких отдельных переключателей — пользователь не обязан думать о типе запроса.

## Scope Boundaries

**В scope:**
- Поиск + flyTo по адресу (DaData)
- Поиск + flyTo + polygon highlight по кадастровому номеру (PKK)
- Замена OpenRailwayMap на ЗОУИТ тайлы Росреестра
- Новая env переменная `NEXT_PUBLIC_DADATA_API_KEY`

**Не в scope:**
- НСПД (nspd.gov.ru) — требует авторизации через Госуслуги, слишком сложно
- Скачивание/экспорт кадастровых данных
- Поиск по координатам (lat, lon) вручную — вторичный сценарий, позже
- Кэширование ответов DaData на бэкенде
- RGIS/ISOGD региональных порталов — данные разрозненные, не масштабируется

## Критерии приёмки

- [ ] Поиск по адресу: ввод 3+ символов → дропдаун с результатами → клик → карта перелетает
- [ ] Поиск по кадастру: ввод `77:01:0001001:1` → карта перелетает, граница участка видна
- [ ] Слой ЗОУИТ видим при zoom ≥ 10 и checkbox "Коммуникации" включён
- [ ] Строка поиска не блокирует переключатели слоёв в тулбаре
- [ ] `tsc --noEmit` без ошибок
- [ ] `NEXT_PUBLIC_DADATA_API_KEY` задокументирован в `.env.example`

## Зависимости

- DaData API ключ (бесплатный аккаунт на dadata.ru)
- Верификация URL тайлового сервиса PKK6/ZONES при реализации (во время planning/work)

## Открытые вопросы

- Нужно ли в будущем поддерживать ввод координат (lat, lon) напрямую? → отложено
- Нужен ли результат поиска в `LocationSection` (маппинг на объект 360°)? → отложено
