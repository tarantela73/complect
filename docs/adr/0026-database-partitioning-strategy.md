# Помесячное секционирование (Monthly Declarative Partitioning) и регламент утилизации данных.

##  1. STATUS

Статус: APPROVED FOR IMPLEMENTATION
Дата: 2026-05-24
Владелец: SRE Team / Lead Database Architect

## 2. CONTEXT

Таблицы common_audit_integrity_logs, common_transactional_outbox и infrastructure_dead_letter_records являются сверхвысоконагруженными точками записи (Write-Heavy Tables) с p99 интенсивностью > 5000 rps.Без секционирования размер этих таблиц за 3 месяца превысит 500 миллионов строк, что приведет к:
1. Деградации дискового I/O из-за вымывания кэша индексов из RAM.
2. Невозможности очистки старых данных (Data Retention) — классический DELETE намертво заблокирует СУБД.
3. Падению SLO Rest API (p95 < 150ms) и Дашборда (p95 < 500ms).

## 3. DECISION

Внедрить Ежемесячное декларативное секционирование (PostgreSQL Monthly Declarative Partitioning BY RANGE) по полю времени created_at / timestamp.
Инженерные правила:
1. Мастер-таблица: Объявляется как партиционированная (PARTITION BY RANGE). Хранение данных в самом мастере запрещено.2. Дочерние секции: Каждая секция хранит данные строго за 1 календарный месяц (например, audit_logs_y2026m05).
3. Автоматизация: Создание секций на следующие 2 месяца вперед делегируется асинхронному Celery-крону celery_beat, исключая падение записи при смене месяца.

## 4. ALTERNATIVES CONSIDERED

TimescaleDB: Отказались. Требует стороннего расширения, нарушает манифест «Postgres Only» без усложнения инфраструктуры.
Плоский DELETE по крону: Отказались. Вызывает критический табличный Bloat и блокировки диска.

## 5. CONSEQUENCES

Pros: Очистка старых данных заменяется моментальной O(1) командой DROP PARTITION без Bloat и блокировок; индексы текущего месяца гарантированно удерживаются в RAM.
Cons: Необходимость строгого контроля за тем, чтобы все поисковые запросы Selectors ВСЕГДА включали поле диапазона времени во избежание сканирования всех секций (Partition Pruning).

## 6. SRE ROLLBACK & RETENTION POLICY

Retention Policy: Данные Outbox хранятся до обработки (но не более 7 дней); данные Аудита и DLQ хранятся в горячем контуре 90 дней, после чего секция отцепляется (DETACH PARTITION), сжимается в pg_dump и улетает на холодное архивное хранение в S3 archive-bucket, а сама секция уничтожается через DROP TABLE.
Rollback Plan: Отключение через слияние секций (MERGE PARTITIONS) обратно в плоскую структуру через временные буферные таблицы.
