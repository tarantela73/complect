# 0009 — PII Vault: AES-256 шифрование и маскирование на Query Side

## 1. Статус

## 2. Контекст

ERP обрабатывает персональные данные граждан (ПДн) в соответствии с ФЗ-152: паспортные данные, СНИЛС, телефоны. Хранение ПДн в открытом виде в PostgreSQL создаёт риск утечки при:

- компрометации базы данных или бэкапа;
- несанкционированном доступе через SQL-консоль или pg_dump;
- случайном логировании запросов (pg_stat_statements, structlog).

Кроме того, UI не должен показывать полные ПДн — только замаскированные значения для идентификации.

---

## 3. Решение

Двухуровневая защита: **шифрование при хранении** + **маскирование при отдаче**.

### Уровень 1 — Шифрование (Command Side)

- Алгоритм: AES-256 через расширение PostgreSQL `pgcrypto` (функции `pgp_sym_encrypt` / `pgp_sym_decrypt`).
- Ключ шифрования: хранится в Docker Secret / HashiCorp Vault, **никогда** в коде или env-файлах.
- Шифруются поля: `passport`, `snils`, `phone` в модели `PersonProfile`.
- Шифрование выполняется в `PiiEncryptionVault` **до** записи в БД; в столбцах хранится ciphertext.
- Логирование операций с ПДн: каждое чтение/запись логируется через `AuditIntegrityEngine` (кто, когда, зачем, `request_id`, `correlation_id`).

### Уровень 2 — Маскирование (Query Side)

Дешифрование происходит только в query-слое при формировании ответа. В API никогда не возвращаются сырые ПДн — только маскированные проекции:

| Поле     | Формат хранения  | Формат в API       |
| -------- | ---------------- | ------------------ |
| passport | ciphertext       | `45**-***888`      |
| phone    | ciphertext       | `+7(999)***-45-67` |
| snils    | ciphertext       | никогда в API      |

Маскирование реализовано в `PersonResponseSchema` через `@field_validator`.

### Правила

- В `SELECT` запросах ПДн-поля **не включаются** если не нужны явно.
- Разлогинивание ключа шифрования из `PiiEncryptionVault` перехватывается с `PermissionDenied` — система fail-closed.
- `snils` не передаётся в API-ответах никогда; используется только для внутренних верификаций.

## 4. Рассмотренные альтернативы

| Альтернатива                     | Причина отказа                                                             |
| -------------------------------- | -------------------------------------------------------------------------- |
| Шифрование на уровне приложения (Python) | Медленнее; ключ нужен в памяти воркера; pgcrypto — проверенный extension. |
| Transparent Data Encryption (TDE) | Не защищает от компрометации через SQL-консоль авторизованным пользователем. |
| Хранение в отдельном vault-сервисе | Избыточная инфраструктура для monolith; latency на каждый запрос.         |

---

## 5. Последствия

### Плюсы

- Компрометация дампа БД не даёт plaintext ПДн.
- UI автоматически получает маскированные данные без дополнительной логики на фронтенде.
- Аудит-лог позволяет расследовать несанкционированный доступ к ПДн.

### Минусы

- `pgcrypto` должен быть установлен на PostgreSQL (расширение, не встроено).
- Поиск по зашифрованным полям невозможен — для поиска по телефону нужен отдельный индекс-хеш (HMAC).
- Ротация ключа шифрования требует перешифрования всех записей (Celery-батч).
