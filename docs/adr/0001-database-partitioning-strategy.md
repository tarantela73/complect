---

## 2. Контекст

Таблицы `common_audit_integrity_logs`, `common_transactional_outbox` и `infrastructure_dead_letter_records` — сверхвысоконагруженные точки записи (Write-Heavy, p99 > 5000 rps).

Без секционирования за 3 месяца объём превысит 500 млн строк, что приведёт к:

- деградации дискового I/O из-за вымывания индексов из RAM;
- невозможности Data Retention — классический `DELETE` блокирует СУБД;
- падению SLO REST API (p95 < 150 ms) и Dashboard (p95 < 500 ms).

---

## 3. Решение

Внедрить ежемесячное декларативное секционирование PostgreSQL (`PARTITION BY RANGE`) по полю `created_at` / `timestamp`.

### Правила

- Мастер-таблица объявляется как партиционированная. Хранение данных в самом мастере **запрещено**.
- Каждая дочерняя секция хранит строго 1 календарный месяц (пример: `audit_logs_y2026m05`).
- Создание секций на следующие 2 месяца вперёд автоматизировано через `celery_beat` — исключает падение записи при смене месяца.
- Retention Policy: Outbox — до обработки, но не более 7 дней; Аудит и DLQ — 90 дней в горячем контуре, затем `DETACH PARTITION` → сжатие в `pg_dump` → холодный S3 archive-bucket → `DROP TABLE`.

### Запреты

- Прямой `DELETE` по диапазону дат — заменяется на `DROP PARTITION`.
- Поисковые запросы без поля диапазона времени (нарушает Partition Pruning).

---

## 4. Рассмотренные альтернативы

| Альтернатива         | Причина отказа                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------- |
| TimescaleDB          | Стороннее расширение. Нарушает манифест «Postgres Only» без усложнения инфраструктуры.      |
| Плоский DELETE по крону | Критический табличный Bloat и блокировки диска при объёмах > 100 млн строк.             |

---

## 5. Последствия

### Плюсы

- Очистка данных — моментальная `DROP PARTITION` O(1), без Bloat и блокировок.
- Индексы текущего месяца гарантированно удерживаются в RAM.
- Автоматический Retention без ручного вмешательства.

### Минусы

- Все `SELECT` на секционированных таблицах **обязаны** включать фильтр по полю диапазона — иначе full scan всех секций.
- Требует мониторинга `celery_beat` для своевременного создания новых секций.
