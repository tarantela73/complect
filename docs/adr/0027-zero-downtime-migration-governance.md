2. CONTEXT
Приложение работает в режиме ASGI Only (Granian/Uvicorn) [4.2] под высокой транзакционной нагрузкой. Классический подход к миграциям (например, добавление поля с NOT NULL или удаление колонки) накладывает на PostgreSQL блокировку AccessExclusiveLock. Это полностью останавливает пишущие и читающие потоки других воркеров, выжигая Error Budget [10.3] и приводя к каскадному падению SLA.
3. DECISION & ENGINEERING LAWНамертво зафиксировать закон Expand & Contract (Расширение и Сужение) для любого изменения схемы данных. Любое деструктивное изменение разбивается строго на 3 релиза:
Релиз N (Expand - Расширение): Добавляется только новое nullable поле или новая таблица. База расширяется. Старый код продолжает читать старое поле.
Релиз N+1 (Switch - Переключение): Накатывается асинхронный Celery-крон (Data Migration), который батчами (по 5000 строк через SKIP LOCKED [12]) копирует данные из старой колонки в новую. Код бэкенда переключается на запись в оба поля одновременно, а чтение переводится на новое поле.
Релиз N+2 (Contract - Сужение): Накладывается NOT NULL констрейнт через валидацию (сначала NOT VALID, затем VALIDATE CONSTRAINT во избежание блокировок). Старая колонка безопасно удаляется из СУБД.
Жесткие запреты на CI/CD (Запрещенные операции):
AddField с флагом NOT NULL без указания default.
RemoveField или AlterField (изменение типа данных), если поле активно используется в текущей ветке master.
Создание индексов без директивы CONCURRENTLY (в Django — через AddIndexConcurrently в pg_catalog).
4. CONSEQUENCES
Pros: 100% аптайм базы данных, нулевые блокировки транзакционного ядра холдинга.Cons: Разработка одной фичи с изменением структуры данных занимает минимум два-три релиза. Скорость разработки (Velocity) приносится в жертву ради абсолютной надежности (Reliability over velocity) [19].
5. SRE ROLLBACK PLANКаждая миграция данных обязана содержать метод reverse_sql или зеркальный шаг backwards() для мгновенного отката схемы СУБД без потери данных, накопленных за время релиза.
