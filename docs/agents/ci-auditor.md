# Ожидание и продолжение CI-аудита

Загружай эту инструкцию при внешнем CI-аудите, ожидании обязательных jobs или
продолжении сохранённого PENDING. Это процесс агента с read-only GitHub-доступом.
Локальные файлы проверяет [CI evidence validator](ci-audit-evidence.md).
При наблюдении и разборе ошибки используй [краткую диагностику](diagnostic-output.md):
сводка и адресный фрагмент в контекст, полные очищенные доказательства в artifacts.

## Начало наблюдения

Получай независимый requirements-файл координатора: repository, обязательные
jobs/artifacts, run/job IDs, run_attempt и ожидаемые head/base/checkout/tree SHA.
Используй согласованный источник требований; не получай их фильтрацией найденных
jobs или копированием из checkpoint. Отсутствующие IDs и SHA не придумывай:
сохрани недостающие сведения и BLOCKED_EVIDENCE; проверяемый checkpoint возможен
только после заполнения обязательного контракта requirements.

Закрепи доступный бюджет времени текущего запуска. Если срок не задан, работай
до доступного лимита запуска; число опросов не является условием завершения.
Сохраняй новые наблюдения и очищенные доказательства в отдельной области
artifacts. Исходные receipts и уже скачанные версии файлов не переписывай.

## Цикл активного запуска

1. Через доступный GitHub connector или `gh api` прочитай актуальные run metadata
   и все страницы jobs нужной попытки. Для REST используй
   `/repos/{owner}/{repo}/actions/runs/{run_id}/attempts/{attempt}/jobs`;
   страницы и `total_count` должны согласоваться. Сопоставь каждый обязательный
   job с выбранным repository/run/attempt/job и ожидаемой source identity.
   Общий conclusion workflow не заменяет conclusions обязательных jobs.
2. Сохрани новый report. Получай доступные обязательные logs/artifacts, сохраняй
   их целиком после очистки секретов, затем запускай валидатор. Наличие файла,
   флаг скачивания или SUCCESS сами по себе не подтверждают доказательство.
   Локальный результат PENDING/ BLOCKED_EVIDENCE не заменяет свежие CI metadata.
3. Пока хотя бы один обязательный job активен или его terminal conclusion ещё
   не получен, оставайся в ожидании. Ожидай ограниченными интервалами 10–30 секунд,
   затем повторяй чтение. Соблюдай rate limits; при сетевом отказе сохраняй причину
   и используй ограниченный backoff в рамках бюджета. Сообщай существенные
   изменения состояния и очередной шаг; неизменный PENDING не завершает задачу.
4. После terminal conclusions всех обязательных jobs проверь полный пакет через
   валидатор. SUCCESS с отсутствующим artifact остаётся BLOCKED_EVIDENCE;
   нарушение хеша/привязки даёт FAIL. Сохраняй исходные отрицательные conclusions,
   verdict и exit даже при неполных доказательствах. Полный отрицательный пакет
   даёт FAIL. PASS допустим только после полного успешного результата валидатора.

При исчерпании бюджета переходи к сохранению checkpoint. Авторизация недоступна
или привязка изменилась — сообщи конкретный блокер, сохрани наблюдение; не объявляй
CI завершённым. Не создавай polling-service, cron, automation или новый чат.

## Сохранение точки продолжения

Используй CLI из [контракта checkpoint](ci-audit-evidence.md#точка-продолжения).
`--save-continuation` сохраняет новую точку для PENDING или BLOCKED_EVIDENCE,
включая независимые требования, наблюдение, проверенные descriptors и недостающие
данные. Запиши возвращённый `continuation_sha256` в родительский индекс приёмки
вместе с путями requirements, report, package и checkpoint. Для следующего вызова
нужен этот независимо сохранённый pin, а не хеш заново прочитанного checkpoint.

Проверь exit команды и наличие выданных пути/pin. Ошибка записи не считается
сохранением точки. Если прежде проверенный файл исчез или изменился, сохрани
старую точку и ошибку проверки; не замещай её новой точкой, забывающей утраченные
доказательства. Если нет валидной полной identity, сохраняй отдельное наблюдение
о блокере и явно укажи, что проверяемый checkpoint не создан.

Заверши текущий запуск статусом ожидания с repository, run IDs/attempts,
обязательными jobs, недостающими данными и путём/pin checkpoint. Это передача
ожидания из-за бюджета, а не завершение CI-аудита. Полный формат находится
в документе валидатора; в сообщение выводи краткую сводку и пути.

## Следующий вызов

Сначала перечитай независимые requirements и свежие GitHub metadata. Перепроверь
repository/run/attempt/job, head/base и привязку фактического checkout/tree;
до получения настоящего checkout proof не подставляй ожидаемые SHA как доказанные.
Продолжай те же run IDs и attempt. Затем передай checkpoint и сохранённый pin
валидатору через `--continuation` и `--continuation-sha256`: он заново проверит
формат, identity и ранее проверенные файлы, после чего оценит свежий report.
Новый PENDING возвращает агента в цикл ожидания, пока остаётся бюджет.

Rerun — новая попытка. Изменение run_attempt, job IDs или source identity не
исправляется заменой значений в старой точке. Зафиксируй новые независимые
requirements, отдельный пакет и checkpoint; прежние наблюдения сохраняй как
историю. Смешивание proof/receipt разных попыток отклоняется. Если pin старой
точки утрачен, не считай её проверенной: выполняй новый независимый аудит
текущего полного пакета либо фиксируй BLOCKED_EVIDENCE.
