# Исправления контрактов после ревью 1281e05

Статус: спецификация согласована пользователем через grill-with-docs
15 октября 2026 года. Решения зафиксированы до начала реализации исправлений.
Исходная спецификация: [infra evidence hardening](2026-10-15-infra-evidence-hardening.md).

## Подтверждённые проблемы

- Прерывание подготовки через KeyboardInterrupt обходит `except Exception`.
  Начальный receipt остаётся с пустым inventory; явный cleanup может вернуть
  PASS при оставшихся ресурсах.
- Канонический список 133 тестов и pytest exit 0 допускают terminal PASS
  при пропущенных setup и отсутствии call. Полная сетка 399 успешных фаз
  сейчас не является условием приёмки.
- Публичная проверка envelope проверяет только переданные записи результатов,
  поэтому отсутствующая обязательная запись не вызывает отказ.

## Согласовано 15 октября 2026 года

1. При Ctrl+C и обрабатываемом SIGTERM предпринимается сохранение частичной
   инвентаризации и очистка подтверждённых собственных ресурсов. Исходная
   причина остановки сохраняется. Если полнота inventory неизвестна,
   cleanup возвращает BLOCKED_STAND, в том числе при пустом списке ресурсов.
   Необрабатываемый обрыв оставляет подготовку незавершённой.
2. При pytest exit 0 пропуск, дубликат, лишняя или отсутствующая фаза
   блокируют приёмку: BLOCKED_STAND, итоговый exit 2. Проверяется точная
   сетка исходных 133 node ID × setup/call/teardown, каждый outcome — passed.
   Исходный manifest сохраняется; отдельная диагностика перечисляет нарушения.
   Уже полученный ненулевой код pytest сохраняется.
3. Положительная приёмка требует явно заданного версионированного контракта
   обязательных результатов. Проверяются записи envelope и сами файлы.
   Отсутствие обязательной записи, файла либо несовпадение хеша блокирует
   приёмку. Целостности произвольного неполного пакета недостаточно.
4. Восстановление inventory после обрыва — отдельное явное действие перед
   cleanup. Оно подтверждает принадлежность по сохранённой идентичности
   стенда, меткам и конфигурации, затем записывает подтверждённые ID для
   последующей очистки. Подготовку и тесты оно не возобновляет. Обычный
   cleanup при неизвестной полноте inventory остаётся заблокированным.
5. Для старых envelope без нового контракта сохраняется отдельный явный
   режим проверки целостности. Приёмка выполняется только по
   версионированному контракту. Старые пакеты остаются читаемыми;
   автоматического назначения профиля приёмки нет.
6. Обязательный legacy-пакет содержит семь результатов:
   manifest с фазами, post-run source check, SQL privilege probes,
   lifecycle journal, identity целевой БД, receipt очистки временных ресурсов
   прогона и итоговый result. Все семь обязательны. Дополнительная
   диагностика разрешена с проверкой хешей; она не заменяет обязательные
   результаты. Очистка полного стенда остаётся отдельным явным действием.

## Проверенные факты для следующего раунда

Текущий envelope имеет format `complect-reviewer-envelope-v1` без профиля
обязательных результатов. Единственный runtime-потребитель helper —
`run_legacy_regressions.py`; CLI и тесты используют также произвольные карты.
Runner сохраняет manifest, post-run sources, privilege probes, lifecycle
journal, target identity и условный cleanup-failure. Итоговый result пишется
после построения envelope. Сам infra CI использует отдельные receipts.

## Приёмка исправлений

Регрессионные проверки через публичные интерфейсы подтверждают:

- Обрабатываемое прерывание сохраняет исходную причину и пытается выполнить
  безопасную очистку. Незавершённый receipt с неизвестной полнотой inventory
  не позволяет объявить cleanup успешным, в том числе с пустым списком.
- Явное восстановление inventory не принимает чужие или несогласованные
  ресурсы и не превращает исходную прерванную подготовку в успешную.
- Отсутствующая фаза, skipped outcome, дубликат, лишняя или некорректная запись
  блокируют приёмку. Положительный случай — ровно 399 успешных фаз исходных
  133 узлов. Исходный manifest и ненулевые коды pytest сохраняются.
- Отсутствие каждого из семи обязательных результатов проверяется отдельно:
  как отсутствующая запись envelope и как отсутствующий файл. Также
  проверяются изменение файла, неподдерживаемая версия контракта и
  дополнительная диагностика с неверным хешем.
- Старый пакет допускает явную проверку целостности, но не получает
  положительную приёмку без нового контракта.

Локальная интеграционная приёмка использует изолированные собственные
ресурсы для прерывания/восстановления/очистки и свежий стенд для полного
исходного прогона 133 тестов. Выполняются общий infra gate и отдельное
Standards/Spec ревью. Полный стенд остаётся локальным этапом; существующий
infra CI получает автоматические регрессионные проверки через ту же команду.

Имена CLI, поля состояния inventory, конкретные версии профиля и безопасный
порядок записи terminal result/envelope определяются при реализации в этих
границах. Успешный result должен быть связан с проверенным полным пакетом;
порядок записи не должен создавать положительную приёмку при частичном сбое.

Открытых вопросов по согласованным границам нет. Отдельный ADR не требуется:
исправляются обратимые контракты инфраструктуры проверки в принятой области.

Исходный список 133 тестов, SQL-защиты, разделение runtime/migrator,
readonly preflight и отдельная очистка полного стенда сохраняются.
Новые доменные понятия не вводятся; CONCEPTS.md не требует изменений.
