# Оркестрация приёмки legacy-стенда

Статус: общий контракт и декомпозиция подтверждены; GitHub Issues опубликованы, реализация ещё не начата.

## Согласовано

Q1: первый объём ограничен пунктами 1 и 2 ретроспективы текущей сессии
feat-015: подтверждённая полная очистка и фиксация источника перед серией
проверок. Focused runtime smoke, политика checkout CI и summary evidence
остаются отдельными предложениями.

Q2: новая команда объединяет только положительный original133: фиксацию
источника, prepare, test, полную очистку и подтверждение отсутствия остатков.
Payments и verifier отказных сценариев сохраняют свои текущие циклы очистки.

Q3: источник новой команды — явно указанный commit SHA. Из него создаётся
отдельная зафиксированная копия. Поддержка dirty snapshot остаётся в
существующих диагностических командах; новая команда её не включает.

Q4: реализация будет в отдельной ветке поверх head PR24 `a19b458`, отдельно
от самого PR24. Способ публикации определён в Q14–Q15.

Q5: после ошибки, SIGINT или SIGTERM сначала останавливается дочерняя
работа своей попытки, затем выполняется guarded cleanup. Диагностика и
первичная причина/код отказа сохраняются. Cleanup не превращает отказ в PASS.

Q6: после SIGKILL или перезапуска машины поддерживается только восстановление
inventory и очистка, без resume original133. Новые тесты требуют новой попытки.
Неясные ownership или состояние прежней работы блокируют recovery.

Q7: baseline проверяется по идентичности ранее существовавших ресурсов;
остатки своей попытки блокируют приёмку. Новые чужие ресурсы допустимы,
не удаляются и не считаются остатками этой попытки.

Q8: frozen source, snapshot, логи и receipts сохраняются до отдельного явного
удаления. Временные credentials и runtime-ресурсы попытки удаляются. Каталог
новой попытки всегда новый; прежние доказательства не перезаписываются.

Q9: разрешены минимальные опциональные параметры prepare/runner для private
runtime paths и журнала ресурсов recovery. Старые вызовы, defaults и форматы
сохраняют поведение.

Q10: orchestration и helpers исполняются из выбранного commit; исходный
checkout служит только bootstrap. Frozen-копия самодостаточна. Commit без
совместимой новой команды и helpers отклоняется до обращения к Docker.

Q11: новый версионированный qualification.json не переопределяет старые
receipts. Тесты exit1 + blocked cleanup дают общий BLOCKED_STAND, сохраняют
primary error и CLI1. Тесты PASS + blocked cleanup дают CLI2. Recovery
подтверждает очистку, но не превращает исходную попытку в PASS.

Q12: приёмка включает реальные original133/399 и Docker-сценарии ошибки,
SIGTERM, SIGKILL с recovery и чужих параллельных ресурсов. Быстрые регрессии
покрывают freeze, journal, ownership и verdict. Full legacy запускается
локально; CI выполняет быстрые проверки инструмента.

Q13: публичный интерфейс — `make legacy-stand-qualify SOURCE_COMMIT=<SHA>
DIRECTORY=<новый каталог>` и `make legacy-stand-recover
DIRECTORY=<каталог попытки>`. Python CLI предоставляет подкоманды run/recover.
Recovery читает исходную идентичность из сохранённой попытки.

Q14: отдельный draft PR направляется в main с явной зависимостью от PR24.
Собственный diff проверяется относительно a19b458. GitHub временно покажет
также изменения PR24; после его слияния может потребоваться перенос новых
коммитов на обновлённый main. Существующие main-only CI triggers сохраняются.

Q15: порядок доставки — локальные проверки и независимое ревью, предъявление
точного commit/патча, отдельное разрешение публикации, затем CI и полная
локальная квалификация фактического checkout SHA. Разрешение публикации PR24
не распространяется на новый PR.

## Подтверждённые факты

Кандидат PR24 имеет head `a19b45803c2eb921ea95eae1b1b1c290e92ae469`.
PR24 открыт, main находится на `20bb9fc0846a13e550f3023d47ddbf286bcbc65f`.
В исходном рабочем дереве много посторонних изменений; их необходимо сохранить.

В кандидате Makefile предоставляет отдельные legacy-stand-prepare,
legacy-stand-test и legacy-stand-cleanup. Runner очищает временный слой
прогона; полный stand и его image очищает prepare_legacy_stand.cleanup.
Разделение описано в docs/development/infra-gates.md:93–103.

prepare проверяет snapshot и создаёт отдельную source copy. Snapshot
поддерживает dirty files; исходное состояние должно оставаться неизменным.
Отдельной команды source freeze/полной квалификации в проверенных CLI нет.
Refusal verifier и Payments уже владеют своей очисткой через finally.
Runner создаёт control и owner-secrets каталоги в /tmp; их пути сейчас
находятся в памяти до finally. Full stand cleanup не удаляет host checkout
или host-side credentials. Обычный cleanup подтверждён прежними receipts;
hard-kill recovery в принятой реализации не проверялся runtime-тестом.
Lifecycle контейнер наследует project/checkout labels через Compose app
anchor; его normal cleanup проверяет оба labels перед удалением.

при вызове to-tickets. Декомпозиция также подтверждена; опубликованы GitHub Issues #26–30.

Проверенный способ доставки учитывает main-only PR triggers Infra и Payments:

## Ограничения

Существующие ownership/fingerprint guards, fail-closed поведение и
контракт исходных 133 node ID / 399 успешных фаз сохраняют силу.
Форматы и команды уже принятой реализации не переопределяются молча.
Решения интервью фиксируются до реализации; итоговое общее понимание
подтверждается пользователем отдельно.


## Предложенная декомпозиция to-tickets

Статус: одобрено и опубликовано. Номера списка соответствуют GitHub Issues
#26, #27, #28, #29, #30 по порядку.
Каждая задача включает свои поведенческие проверки и совместимость старых CLI.

1. Запуск из самодостаточного frozen commit. Без блокеров. Bootstrap принимает
   SHA и свежий каталог, создаёт независимую копию и передаёт исполнение её
   версии команды; несовместимый commit отклоняется до Docker. Проверки:
   mutable checkout и shared Git objects не нужны после freeze, повторное
   использование каталога запрещено. Промежуточный preflight не выдаёт PASS
   квалификации до реализации полного цикла в задаче 2.
2. Полный положительный цикл original133 с подтверждённой очисткой. Блокирует 1.
   Публичная команда выполняет prepare/test/cleanup, проверяет baseline identities
   и собственные остатки, ведёт durable inventory/private paths и новый
   qualification.json. Принимает ровно 133 исходных узла/399 успешных фаз;
   cleanup blocked после PASS даёт CLI2. Сохраняет source/evidence, удаляет
   runtime credentials. Реальный успешный цикл и чужие параллельные ресурсы.
3. Безопасное завершение при ошибке, SIGINT и SIGTERM. Блокирует 2.
   Остановка своей дочерней работы предшествует guarded cleanup. Первичная
   причина и код сохраняются; тесты exit1 плюс blocked cleanup дают
   BLOCKED_STAND/CLI1. Реальные Docker fault/signal проверки.
4. Cleanup-only recovery после SIGKILL. Блокирует 3.
   Команда recover читает идентичность попытки, восстанавливает inventory и
   безопасно очищает ресурсы/credentials после hard-kill. Неясное ownership или
   состояние прежней работы даёт BLOCKED_STAND. Повторная очистка безопасна,
   тесты не возобновляются, исходный verdict не повышается. Реальный SIGKILL
   с новым процессом recovery и проверки повреждённого/неполного журнала.
5. Проверка и доставка общего кандидата. Блокируют 1–4.
   Быстрые регрессии подключены к CI, существующие main-only triggers сохранены.
   Независимое ревью собственного diff от a19b458 и локальные проверки дают
   точный commit/patch для отдельного разрешения публикации. После разрешения:
   draft PR в main с зависимостью от PR24, CI и полная локальная квалификация
   фактического checkout SHA. До разрешения публикация остаётся ожидающим шагом.
