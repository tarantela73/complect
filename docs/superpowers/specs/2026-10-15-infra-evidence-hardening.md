# Надёжность инфраструктурных проверок и evidence

Статус: спецификация согласована пользователем через grill-with-docs
15 октября 2026 года. Решения ниже зафиксированы до начала реализации пунктов 2–6.
Область: пункты 2–6 ретроспективы 14 октября 2026 года. Пункт 1 исправлен
в коммите 10b8bd4f18a17c6ff5b2daea70da48b8867757f8.

## Согласовано 15 октября

1. При сжатом или искажённом выводе читать точное содержимое небольшими
   фрагментами из сохранённого файла с проверкой версии. Хеш подтверждает
   идентичность, но не заменяет чтение. Недоступность оригинала блокирует
   вывод о корректности. Настройки MCP и плагинов требуют отдельного разрешения.
2. Ruff, mypy и actionlint обязательны в существующем infra workflow и доступны
   через ту же локальную команду. Область инфраструктурных файлов задаётся явно;
   ошибка блокирует gate. Расширение на весь backend согласуется отдельно.
3. Отдельная команда готовит свежий изолированный стенд, выдаёт данные для
   существующего preflight и управляет только собственными ресурсами.
   Preflight остаётся проверкой без автоматического исправления. При неполной
   подготовке сохраняются причина отказа и данные для безопасной очистки.
4. После исходных 133 тестов и до cleanup повторно проверяются исходный snapshot
   и подготовленная source copy. Изменение блокирует приёмку даже при успешных
   тестах. Результаты сохраняются, безопасная очистка продолжается. Повторный
   прогон запускается явно после подготовки согласованной версии исходников.
5. Reviewer начинает с одного обязательного файла, связывающего хеши исходников
   и патча, image ID, run ID, точные пути результатов и их хеши. Отсутствие или
   несовпадение обязательного артефакта блокирует приёмку. Автоматический выбор
   последнего успешного результата запрещён.
6. Ошибка подготовки останавливает её дальнейшие шаги. Сохраняется диагностика,
   предпринимается безопасная очистка подтверждённых собственных ресурсов;
   остатки сообщаются отдельно. Следующий запуск создаёт новый стенд.
   Восстановление незавершённого стенда требует отдельного явного действия.
7. Существующий infra CI получает статические проверки и автоматические
   регрессионные тесты. Полный цикл подготовки стенда и исходные 133 теста
   входят в локальную приёмку. Перенос полного стенда в CI — отдельный этап.
8. После успешной подготовки стенд остаётся для явного запуска проверок.
   Проверки удаляют свои временные контейнеры. Отдельная команда очистки стенда
   использует сохранённую запись принадлежности и повторно проверяет владение
   перед удалением его ресурсов. Ошибка очистки блокирует полную приёмку.
9. Статические инструменты поставляются в заранее собранном тестовом
   Docker-образе на основе locked backend. Ruff и mypy берутся из существующего
   lock; actionlint закрепляется версией и SHA-256. Загрузки выполняются при
   сборке образа; сам gate работает без сети. Отсутствующий инструмент вызывает
   отказ проверки.

## Проверенные исходные факты

- `infra-tests.yml` вызывает `make agent-infra-test`; статические проверки
  пока не включены в этот gate.
- `run_legacy_regressions.py` проверяет snapshot и source copy через preflight
  до запуска; повторной проверки после pytest перед cleanup пока нет.
- Отдельной команды полного приготовления изолированного стенда пока нет.
- Данные source/image/run/result существуют в отдельных артефактах;
  единого обязательного reviewer envelope пока нет.

## Приёмка

Автоматические регрессионные проверки покрывают отказ при недоступном точном
артефакте, ошибки статических инструментов, изменение snapshot/source copy,
неполный или несогласованный envelope, сбой подготовки и отказ очистки.
Существующие проверки принадлежности ресурсов сохраняются.

Локальная приёмка включает подготовку свежего стенда, существующий readonly
preflight, исходные 133 теста, повторную проверку snapshot и подготовленной
source copy перед cleanup, проверку пакета evidence и явную очистку стенда.
Успешные тесты не перекрывают ошибки источников, evidence или cleanup.

CI использует ту же локальную команду infra gate со статическими инструментами
и автоматическими регрессионными проверками. Реальное выполнение GitHub Actions
оценивается отдельно от локальной проверки команды и workflow.

## Границы

Публичные форматы диагностики, исходный manifest 133 тестов, SQL-защиты и
разделение runtime/migrator остаются требованиями при обсуждении реализации.
Существующие диагностические поля, статусы и сообщения сохраняются; новые
проверки не дают права ослаблять защиты ради успешного запуска.

Решения обратимы и относятся к инфраструктуре проверки, поэтому отдельный ADR
не требуется. Новые доменные понятия не вводятся; CONCEPTS.md не изменяется.
Открытых вопросов по согласованным границам нет. Конкретные имена CLI,
пути артефактов и перечень статически проверяемых инфраструктурных модулей
определяются при подготовке реализации в пределах этой спецификации.
