# Defer 1С integration — bank statement import first

## Context

ERP "Комплект" развёртывается в компании ~10 человек, где бухгалтер продолжает работать в 1С как в основном инструменте. Finance-домен ERP находится в стадии формирования — транзакционная модель, матчинг платежей и отчётность ещё не реализованы. Запрос на двустороннюю синхронизацию с 1С возникает естественно, но на текущей стадии он приоритизируется ниже bank statement import.

## Guidance

**Этап 1 — Bank Statement Import (✓ реализован):**
Загрузка файла выписки, парсинг, предпросмотр с возможностью отмены, создание `BankStatement` + `BankStatementLine` записей. Первый реализованный формат — 1С Client Bank Exchange (КЛ→1С); парсер расширяем для MT940/CAMT.053. Закрывает основную боль — сверку платежей — без касания 1С.

**Этап 2 — Auto-matching:**
Автоматическое сопоставление входящих платежей с контрактами по триаде: сумма + контрагент + расчётный период. Снижает ручную работу на 80%+ для типовых платежей.

**Этап 3 — Reporting:**
Отчёт по оплатам/задолженности. Уведомления о просроченных платежах (push/email/Telegram).

**Этап 4 — 1С integration (отложено):**
Интеграция 1С ↔ ERP откладывается до полной миграции бухгалтера в ERP. Только тогда задача синхронизации становится осмысленной — не параллельная работа двух систем, а миграция с легаси-инструмента.

## Why This Matters

**Dual source-of-truth.** Если бухгалтер работает в 1С, а данные дублируются в ERP, любое расхождение создаёт организационный конфликт: обе системы "правые" с точки зрения пользователей. Это нельзя решить кодом.

**Maintenance burden.** 1С регулярно обновляется. Каждый релиз потенциально ломает интеграцию. Для команды ~10 человек это периодические неотложные баги без бизнес-ценности.

**ROI-мисматч.** Несколько недель разработки + ongoing поддержка дают значительно меньше пользы, чем bank import за 1–2 недели. Bank import решает ту же проблему сверки платежей с 5% усилий.

**Правильный порядок.** Сначала ERP должен стать достаточно удобным, чтобы бухгалтер захотел перейти. Интеграция с 1С нужна для миграции данных при переходе — не для параллельной работы двух систем.

## When to Apply

Откладывать 1С-интеграцию и приоритизировать bank import, если **хотя бы одно** условие выполнено:

- Бухгалтер использует 1С как основной рабочий инструмент (не ERP)
- Размер команды < 30 пользователей
- Finance-домен ERP не является source of truth
- Интеграция требует two-way sync (не однонаправленной миграции)

Интеграция 1С ↔ ERP становится обоснованной, когда **все три** условия выполнены:

- Бухгалтер работает преимущественно в ERP, 1С — вторичный инструмент
- Команда 30–50+ человек (ROI оправдывает maintenance cost)
- Finance-домен ERP покрывает полный цикл: импорт → матчинг → отчётность → согласования

## Examples

**Bank Import (✓ реализован — Этап 1):**

| Аспект | Детали |
|---|---|
| Что реализовано | Загрузка файла, парсинг 1С Client Bank Exchange (КЛ→1С), `BankStatement` + `BankStatementLine`; форматы MT940/CAMT.053 — следующий шаг |
| Effort | 1–2 недели |
| Ongoing maintenance | Минимальный: форматы меняются редко |
| Что даёт | Сверка платежей, матчинг к контрактам (Этап 2), отчёт по задолженности (Этап 3) |
| Risk | Низкий: если парсер сломался — загрузи файл вручную |

**1С Integration (отложено):**

| Аспект | Детали |
|---|---|
| Что реализуется | API/COM-интеграция, маппинг объектов, two-way sync, conflict resolution |
| Effort | Несколько недель + интеграционное тестирование |
| Ongoing maintenance | Высокий: каждый релиз 1С — потенциальный breaking change |
| Что даёт | Данные из 1С в ERP (бухгалтер всё равно работает в 1С) |
| Risk | Высокий: расхождение данных трудно детектировать и объяснять |

Bank import даёт 80% ценности 1С-интеграции при 5% затрат.
